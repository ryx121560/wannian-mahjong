# 游戏状态持久化与积分重置 Spec

## 1. 背景

当前页面刷新后会重新发牌并开始一局新游戏，所有未完成牌局状态都会丢失。积分虽然具备保存能力，但页面初始化仍会无条件调用 `newGame()`，导致“刷新页面”和“开始新游戏”两个行为没有区分。

产品期望：

- 刷新页面后恢复上一局未完成的游戏。
- 只有玩家主动点击“新游戏”时才开始一局新游戏。
- 所有玩家积分跨页面刷新和跨牌局保留。
- 只有任意玩家积分小于或等于 0 时，才将四名玩家积分统一重置为 100。

## 2. 产品目标

- 页面刷新不会重新洗牌、发牌或重置回合。
- 未完成牌局可以恢复到刷新前的可继续操作状态。
- 积分在正常对局结束、刷新和主动开始下一局时持续累计。
- 破产重置是唯一自动将四名玩家积分恢复为 100 的业务场景。
- 游戏初始化、状态恢复和主动新游戏具有清晰且互斥的行为。

## 3. 非目标

- 本阶段不支持多设备同步未完成牌局。
- 本阶段不支持多个浏览器标签页同时操作同一牌局。
- 本阶段不保存动画播放进度和定时器剩余毫秒数。
- 本阶段不修改胡牌、计分和 AI 决策规则。
- 本阶段不引入数据库或第三方状态管理依赖。

## 4. 核心规则

### 4.1 页面首次访问

当本地不存在有效游戏快照时：

- 页面保持空闲状态。
- 不自动调用 `newGame()`。
- 不自动洗牌或发牌。
- 提示玩家点击“新游戏”开始。
- 从现有积分存储中加载四名玩家积分；若积分也不存在，默认均为 100。

### 4.2 刷新页面

当存在有效的未完成牌局快照时：

- 恢复牌墙及其原有顺序。
- 恢复四名玩家的手牌、副露和积分。
- 恢复牌河、当前玩家、庄家、回合数和游戏阶段。
- 恢复最后一张弃牌及响应上下文。
- 不重新洗牌、不重新发牌、不调用 `newGame()`。
- 根据恢复后的阶段重新渲染界面，并继续等待玩家操作或安排 AI 后续行动。

刷新不能改变任何玩家的积分、手牌数量、牌墙顺序或当前行动方。

### 4.3 已结束牌局刷新

牌局已经胡牌或流局时：

- 保存最终积分和结束状态。
- 刷新后不得自动开始下一局。
- 页面显示上一局已结束状态，并等待玩家点击“新游戏”。
- 不重复结算、不重复增加总局数、不重复执行破产检查。

### 4.4 点击“新游戏”

只有以下操作允许调用 `newGame()`：

- 玩家主动点击“新游戏”。
- 自弈模式根据其既有流程明确开始下一局。

普通模式下点击“新游戏”时：

- 保留当前累计积分。
- 清除上一局游戏快照。
- 重新洗牌和发牌。
- 创建并立即保存新牌局快照。

若当前仍有未完成牌局，点击“新游戏”会直接放弃该局并开始新局。本阶段不新增二次确认弹窗。

### 4.5 破产重置

每局完成积分结算后检查四名玩家积分：

- 任意玩家积分小于或等于 0，判定该玩家破产。
- 将四名玩家积分统一重置为 100。
- 保存重置后的积分。
- 当前牌局保持结束状态，不自动开始下一局。
- 告知玩家破产玩家和积分已统一重置。

除破产外，以下行为均不得重置积分：

- 刷新页面。
- 关闭后重新打开页面。
- 点击“新游戏”。
- 流局。
- 普通玩家胡牌。
- 本地游戏快照损坏或缺失。

## 5. 持久化方案

### 5.1 推荐方案

采用两层持久化：

- 积分继续使用现有积分保存接口，作为累计积分的持久数据源。
- 当前牌局使用 `localStorage` 保存版本化游戏快照，负责页面刷新恢复。

选择该方案的原因：

- 复用现有积分接口和游戏日志存储方式。
- 不需要新增数据库表或第三方依赖。
- 未完成牌局只要求在当前浏览器中恢复，本地快照满足产品范围。

### 5.2 不采用的方案

- 仅保存积分：不能恢复手牌、牌墙和回合，不满足需求。
- 将完整牌局保存到现有 RL 配置接口：会混合不同职责，增加数据损坏风险。
- 新增服务端数据库牌局表：可以支持跨设备恢复，但超出当前需求和改造范围。

## 6. 游戏快照结构

快照必须包含版本号和恢复游戏所需的业务状态，示意结构如下：

```text
GameSnapshot
  version
  savedAt
  status
  wall
  players
    name
    human
    score
    hand
    melds
  discards
  playerDiscards
  lastDiscard
  lastDiscardP
  cur
  dealer
  turn
  phase
  canP / canK / canW / canWS
  responseContext
  kongContext
  newDrawnTile
  newDrawnIdx
  currentGameLog
```

不保存以下临时状态：

- Canvas 点击热区。
- DOM 节点和渲染缓存。
- `setTimeout` 返回值。
- AI 弃牌动画的中间帧。
- 玩家当前抬起但尚未打出的选中牌。

恢复后这些状态应重新计算或清空。

## 7. 保存时机

采用“关键动作后立即保存”，至少覆盖：

- 新游戏完成发牌后。
- 任意玩家摸牌后。
- 任意玩家弃牌后。
- 碰、明杠、暗杠、加杠后。
- 玩家选择过牌后。
- 当前行动方或游戏阶段发生变化后。
- 胡牌或流局完成结算后。
- 破产积分重置后。
- 自弈模式切换导致玩家身份或阶段变化后。

保存操作失败不得中断当前游戏，但应输出可定位的错误日志。

## 8. 页面初始化流程

```text
加载牌面资源
  -> 加载累计积分
  -> 读取并校验游戏快照
  -> 存在有效快照：恢复状态
  -> 不存在有效快照：进入 idle 状态
  -> 重新渲染页面和按钮
  -> 若轮到 AI：根据当前 phase 安排一次后续行动
  -> 若轮到玩家：等待玩家继续操作
```

初始化流程不得直接调用 `newGame()`。

## 9. AI 与计时器恢复

定时器不直接保存。恢复后根据游戏阶段重建行为：

- `drawing` 且当前为 AI：重新安排 AI 摸牌。
- `discarding` 且当前为 AI：重新安排 AI 弃牌。
- `discarding` 且当前为玩家：等待玩家出牌。
- `responding` 且响应方为 AI：重新计算或恢复响应并安排 AI 行动。
- `responding` 且响应方为玩家：重新显示碰、杠、胡、过按钮，并重新开始完整响应倒计时。
- `ended` 或 `idle`：不安排 AI 行动。

恢复逻辑必须保证同一个动作只执行一次，避免重复摸牌、重复弃牌和重复结算。

## 10. 数据校验与异常处理

读取快照时至少校验：

- 快照版本受支持。
- 四名玩家数据完整。
- 当前玩家和庄家下标在 `0-3` 范围内。
- `phase` 属于允许的游戏阶段。
- 手牌、牌墙和牌河中的牌可以正常反序列化。
- 积分为有效数值。

快照无效或无法解析时：

- 删除无效快照。
- 保留从积分接口加载的累计积分。
- 页面进入空闲状态。
- 不自动开启新游戏。
- 不将积分重置为 100，除非积分本身不存在或此前已触发破产规则。

## 11. 验收标准

### 11.1 刷新恢复

- 玩家摸牌后刷新，恢复后仍为同一张摸牌、同一手牌和同一牌墙剩余数。
- 玩家选择一张牌但未弃出时刷新，恢复牌局但清空临时选中状态。
- AI 回合刷新后，AI 只继续执行一次当前动作。
- 碰、杠或等待响应阶段刷新后，可以继续完成该阶段。
- 连续刷新两次不会改变手牌、积分、牌墙和当前行动方。

### 11.2 新游戏

- 首次访问且无快照时不自动发牌。
- 点击“新游戏”后才创建牌局并完成发牌。
- 未完成牌局中点击“新游戏”会重新发牌，但保留累计积分。
- 已结束牌局刷新后不会自动开始下一局。

### 11.3 积分

- 正常结算后刷新，积分与刷新前一致。
- 点击“新游戏”不会将积分恢复为 100。
- 任意玩家积分大于 0 时，不触发统一重置。
- 任意玩家积分小于或等于 0 时，四名玩家积分统一重置为 100。
- 快照损坏时保留有效累计积分，不触发积分重置。

### 11.4 防重复

- 恢复已结束牌局不会重复计算得分。
- 恢复 AI 回合不会重复摸牌或弃牌。
- 恢复响应阶段不会重复碰、杠、胡或过牌。
- 页面初始化过程中不会间接调用两次新游戏。

## 12. 实施优先级

### P0：基础恢复

- 移除页面加载时无条件调用 `newGame()` 的行为。
- 新增游戏快照保存、读取、校验和清理能力。
- 实现玩家回合和已结束状态的刷新恢复。

### P1：完整阶段恢复

- 恢复 AI 回合、响应阶段、碰杠上下文和相关按钮。
- 增加防重复执行保护。

### P2：稳定性

- 增加快照版本迁移或失效策略。
- 增加快照异常日志和关键状态审计信息。

## 13. 上线建议

先完成 P0，并验证普通玩家回合、未完成牌局和已结束牌局的刷新行为。随后完成 P1，覆盖 AI 和响应阶段。积分重置规则应与状态恢复同时验收，避免修复刷新后仍因初始化兜底逻辑错误重置积分。
