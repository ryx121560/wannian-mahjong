# PRD：阶段一「规则与评测基础」

## 1. 背景

当前万年麻将已经具备基础对局、胡牌判断、AI 出牌、AI 日志、MCTS/RL 实验入口和标准 AI 牌例。但从产品体验看，用户仍会遇到两个核心问题：

1. AI 偶尔出牌不合理，用户难以判断是 AI 策略问题，还是规则判断本身不稳定。
2. 当前规则逻辑仍较多分散在运行代码中，真实规则、当前实现、AI 决策依据之间缺少统一产品口径。

因此阶段一不追求“AI 立刻变强”，而是先把规则、牌例、计分和回归验证做扎实，为后续强规则 AI、MCTS、对手建模和训练模型打基础。

## 2. 产品目标

阶段一目标：建立一套可信、可解释、可回归的万年麻将规则与评测基础。

具体目标：

- 明确真实万年麻将规则口径。
- 固化胡牌、听牌、碰、杠、万能牌、打烂、半正宗、全正宗、计分等边界。
- 建立规则引擎的产品接口定义，后续由研发实现。
- 建立约 50 个标准牌例，用于验证规则、计分和 AI 底线行为。
- 建立命令行回归能力，让每次 AI 或规则调整后都能判断是否退化。
- 保证当前 HTML 游戏入口仍可正常运行，不要求一次性重构成 React 页面。

## 3. 非目标

阶段一不做以下事情：

- 不重写 AI 候选弃牌评分模型。
- 不引入新的机器学习模型。
- 不引入新依赖。
- 不做数据库改造。
- 不实现吃牌。
- 不做页面内自动化测试面板。
- 不把当前 HTML 游戏一次性迁移到 React/Next 页面。
- 不以 MCTS/RL 作为普通对局默认主策略。

## 4. 规则范围

### 4.1 基础规则

阶段一产品规则口径如下：

- 四人麻将。
- 1 名真人玩家，3 名 AI 玩家。
- 不支持吃牌。
- 支持碰。
- 支持明杠。
- 支持暗杠。
- 支持加杠。
- 支持胡牌。
- 支持自摸。
- 支持点炮。
- 支持抢杠。
- 支持杠开。

### 4.2 胡牌路线

阶段一需要明确并验收以下胡牌路线：

- 普通面子手。
- 七对子。
- 打烂。
- 半正宗。
- 全正宗。

每一种路线都需要有标准牌例覆盖，包括：

- 可胡案例。
- 不可胡案例。
- 边界案例。
- 容易误判案例。

### 4.3 万能牌 / 假胡

阶段一采用以下规则口径：

- 不做固定翻牌万能。
- 不做每局固定万能牌。
- 万能牌规则仅来自“杠后摸牌触发的万能/假胡”。
- 具体触发条件、能否替代、是否影响计分，需要在规则文档中明确写出，并进入标准牌例。

## 5. 计分范围

阶段一不仅验证“能不能胡”，也要验证“胡了以后怎么算分”。

计分验收需要覆盖：

- 点炮结算。
- 自摸结算。
- 抢杠结算。
- 杠开结算。
- 普通面子手分数。
- 七对子分数。
- 打烂分数。
- 半正宗分数。
- 全正宗分数。
- 复合番型时的分类优先级。

计分结果必须能输出：

- 胡牌玩家。
- 支付玩家。
- 胡牌类型。
- 番型分类。
- 每位玩家分数变化。
- 结算说明。

## 6. 规则引擎产品接口

阶段一要求研发建立 TypeScript 规则源头，建议目录为：

```text
src/game/rules
```

产品层面需要定义以下能力，不要求产品负责代码实现。

### 6.1 `canWin(hand, context)`

用于判断某副手牌是否可以胡。

返回内容应包含：

- 是否可胡。
- 胡牌路线。
- 胡牌番型。
- 是否使用万能牌。
- 失败原因。

### 6.2 `getShanten(hand, context)`

用于判断当前手牌向听状态。

返回内容应包含：

- 综合向听数。
- 普通面子手向听。
- 七对子向听。
- 打烂向听。
- 半正宗向听。
- 全正宗向听。
- 当前推荐路线。

### 6.3 `getLegalActions(state, playerId)`

用于判断玩家当前合法动作。

返回动作包括：

- 胡。
- 自摸。
- 碰。
- 明杠。
- 暗杠。
- 加杠。
- 过。
- 出牌。

不包含吃牌。

### 6.4 `scoreSettlement(winResult, state)`

用于结算分数。

返回内容应包含：

- 每位玩家结算前分数。
- 每位玩家结算后分数。
- 每位玩家分数变化。
- 支付关系。
- 结算原因。

### 6.5 `classifyHand(hand, context)`

用于识别牌型。

返回内容应包含：

- 平胡。
- 七对。
- 打烂。
- 半正宗。
- 全正宗。
- 混一色。
- 清一色。
- 碰碰胡。
- 其他当前产品已支持的番型。

## 7. 当前 HTML 游戏接入原则

当前真实运行入口仍是：

```text
public/game/wannian-mahjong.html
```

阶段一不要求一次性废弃该入口。

接入原则：

- TypeScript 规则引擎作为长期源头。
- 通过 public 适配层供当前 HTML 游戏调用。
- HTML 继续负责 UI、动画、玩家交互和现有对局编排。
- 规则判断、胡牌判断、计分判断逐步委托给规则引擎。
- 迁移过程中不能破坏刷新恢复、积分结算、AI 日志和新游戏流程。

## 8. 标准牌例集

阶段一标准牌例规模建议约 50 个。

### 8.1 保留现有 AI 牌例

保留现有 20 个 AI 标准牌例，用于验证 AI 底线行为：

- 不无理由拆完整面子。
- 不无理由拆关键对子。
- 不无理由拆有效搭子。
- 听牌后不乱改良。
- 杠牌不破坏原有听牌。
- MCTS/RL 不覆盖明显更优规则结果。

### 8.2 新增约 30 个规则与计分牌例

新增牌例类型：

- 普通面子手胡牌。
- 七对子胡牌。
- 打烂胡牌。
- 半正宗胡牌。
- 全正宗胡牌。
- 不能胡的边界牌。
- 万能牌/假胡。
- 可碰。
- 不可碰。
- 可明杠。
- 不可明杠。
- 可暗杠。
- 加杠。
- 抢杠。
- 杠开。
- 点炮计分。
- 自摸计分。
- 特殊牌型计分。
- 番型分类优先级。

每个牌例至少包含：

```json
{
  "id": "rule-case-001",
  "title": "普通面子手胡牌",
  "hand": [],
  "context": {},
  "expected": {
    "canWin": true,
    "route": "normal",
    "handType": "平胡",
    "scoreDelta": []
  }
}
```

## 9. 回归验证

阶段一需要建立命令行回归能力。

产品期望：

- 一条命令可以运行全部标准牌例。
- 输出通过数量。
- 输出失败数量。
- 输出失败牌例 ID。
- 输出实际结果和期望结果差异。
- 任一失败都不能被忽略。
- AI 或规则改动后必须运行回归。

示例输出：

```text
Rule regression completed
Passed: 48
Failed: 2

Failed cases:
- rule-case-017 抢杠计分错误
  expected: payer=AI下家, delta=-4
  actual: payer=all, delta=-4

- ai-case-011 听牌危险牌回避失败
  expected: discard=wan2
  actual: discard=wan8
```

## 10. AI 阶段一边界

阶段一不做强规则 AI 重构。

AI 只要求满足底线：

- 规则迁移后 AI 行为不能明显退化。
- 现有 20 个 AI 标准牌例应继续通过。
- AI 日志继续保留决策来源、路线、向听、候选、原因。
- 普通对局默认仍走稳定规则路径。
- MCTS/RL 仍为显式开关或自弈训练能力，不作为默认主策略。

阶段二才进入：

- 候选弃牌统一评分。
- 有效进张数量。
- 听牌质量。
- 剩余枚数。
- 防守评分。
- 分数位置策略。

## 11. 验收标准

阶段一完成后，应满足以下验收条件：

- 有完整规则文档，明确真实规则口径。
- 有 TypeScript 规则引擎接口定义。
- 当前 HTML 游戏仍可正常运行。
- 不支持吃牌这一点在规则文档和交互中保持一致。
- 胡牌、听牌、碰、杠、万能牌、打烂、半正宗、全正宗、计分都有标准牌例。
- 标准牌例总量约 50 个。
- 命令行回归可以稳定运行。
- 规则回归全部通过。
- 现有 20 个 AI 标准牌例不退化。
- AI 决策日志仍可用于复盘“不合理出牌”。

## 12. 研发交付物

研发应交付：

- 规则 PRD 文档：`docs/ai-rule-engine-prd.md`
- 规则说明文档更新：`docs/rules.md`
- 标准牌例数据：`docs/ai-standard-cases.json` 或新的规则 fixture 文件。
- TypeScript 规则模块：`src/game/rules`
- public 适配层：供 `public/game/wannian-mahjong.html` 调用。
- 命令行回归脚本。
- 阶段一实现状态文档：记录已完成、未完成、已知限制。

## 13. 推荐迭代顺序

1. 固化真实规则文档。
2. 补齐规则与计分牌例。
3. 建立 TypeScript 规则接口。
4. 建立命令行回归脚本。
5. 将胡牌和向听判断接入规则引擎。
6. 将计分判断接入规则引擎。
7. 将碰杠合法性判断接入规则引擎。
8. 回归现有 20 个 AI 牌例。
9. 输出阶段一实现状态文档。

## 14. 风险

主要风险：

- 真实万年麻将规则和当前代码行为存在差异。
- 一次性迁移完整规则引擎可能影响现有对局稳定性。
- 特殊牌型和计分优先级如果不先确认，容易反复返工。
- AI 出牌问题可能被误归因，实际根因可能是规则、向听或日志不一致。

规避方式：

- 以真实规则为最终口径。
- 所有差异进入标准牌例。
- 分层迁移，不一次性替换整个游戏状态机。
- 每次改动后跑规则回归和 AI 牌例回归。
